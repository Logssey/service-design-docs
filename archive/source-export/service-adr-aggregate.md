### **ADR-001 — 백엔드 프레임워크로 Spring Boot 채택**

**상태** Accepted

**맥락**

5인 팀, 구축 기간 3주. 인증·인가, 소유권 검증, 트랜잭션 처리가 핵심이며 99개 기능 요구사항을 구현해야 한다. 새로운 기술 학습에 쓸 시간이 없다.

**결정**

- Spring Boot 3.x, Java 21
- 빌드 도구는 Gradle
- 영속성 계층은 JPA(Hibernate) + QueryDSL
- 인증·인가는 Spring Security 사용
- API 문서는 springdoc-openapi로 생성

**근거**

- 팀 내 경험자 확보가 가장 용이하고 국내 레퍼런스가 많다
- Spring Security가 인증·인가 골격을 제공하여 `NFR-AUTH-006`~`010` 충족에 유리하다
- QueryDSL은 `FR-LIST-008`, `FR-LIST-009`의 다중 조건 검색·정렬 조합에 적합하다

**대안**

- NestJS: 프론트와 언어 통일 가능하나 팀 숙련도가 낮고 구조를 직접 잡아야 한다
- FastAPI: 개발 속도는 빠르나 인증·권한 체계를 전부 구현해야 한다

**결과**

- 초기 설정과 빌드 시간이 상대적으로 길다
- JPA의 N+1 문제에 대한 대응이 필요하다
- Swagger UI는 운영 환경 노출 정책을 별도로 정해야 한다

**관련 요구사항** FR 전체, NFR-AUTH-006~010

### **ADR-002 — 채팅 서버를 독립 워크로드로 분리**

**상태** Accepted

**맥락**

`FR-CHAT-002`는 실시간 메시지 송수신을 요구한다. WebSocket 연결은 API 요청과 근본적으로 다른 자원 사용·수명주기 특성을 가진다.

| **구분** | **API 서버** | **채팅 서버** |
| --- | --- | --- |
| 연결 | 무상태, 단발 요청 | 상태 보유, 장기 연결 |
| 자원 | CPU 중심 | 연결당 메모리 점유 |
| 재시작 영향 | 일부 요청 실패 | 전체 연결 단절 |

**결정**

- 채팅 서버를 API 서버와 분리된 워크로드로 운영한다
- 구현은 Node.js + Socket.IO를 사용한다
- 메시지 저장과 이력 조회는 API 서버가 담당하고, 채팅 서버는 실시간 전달만 담당한다
- 다중 인스턴스 간 메시지 전달은 Redis Pub/Sub을 사용한다
- WebSocket 연결 수립 시 토큰 검증과 대화방 참여 권한을 확인한다

**근거**

- 배포 주기와 스케일 기준을 독립적으로 관리할 수 있다
- Socket.IO는 재연결, 룸 관리, Redis 어댑터를 기본 제공한다
- Spring WebSocket + STOMP 대비 다중 인스턴스 구성이 단순하다

**대안**

- Spring 내 WebSocket 통합: 언어 단일화는 가능하나 배포 결합과 다중 인스턴스 구성 부담이 있다
- 폴링 방식: 구현은 단순하나 사용자 경험이 저하된다

**결과**

- 팀이 Java와 TypeScript 두 언어를 다뤄야 한다
- 메시지 저장(API)과 전달(채팅 서버) 경로가 분리되어 디버깅 지점이 늘어난다
- 전달 실패 시에도 저장된 메시지는 API 조회로 복구 가능해야 한다

**관련 요구사항** FR-CHAT-001~006, NFR-AUTH-011, NFR-AVAIL-005

### **ADR-003 — 챗봇을 API 서버에 통합하고 어댑터로 경계 분리**

**상태** Accepted

**맥락**

챗봇은 외부 LLM API를 호출하는 단발 HTTP 요청이며 호출 빈도가 낮다. `NFR-EXT-001`은 외부 연동 실패가 전체 장애로 확산되지 않을 것을 요구한다.

**결정**

- 챗봇 기능은 API 서버 내 모듈로 구현한다
- LLM 호출은 공급자 중립 어댑터 인터페이스 뒤에 둔다
- 챗봇 전용 스레드 풀을 분리하여 API 서버의 다른 기능에 영향을 주지 않도록 한다
- 외부 호출에는 타임아웃과 재시도 제한을 적용한다
- 기능 비활성화 스위치를 제공한다

**근거**

- 별도 서버로 분리하면 서비스 간 인증이라는 새로운 문제가 발생하며, 3주 일정에서 이를 적절히 처리하기 어렵다
- 호출량이 적어 독립 워크로드를 상시 유지할 이유가 없다
- 어댑터 경계를 두면 기능 확장 시 별도 서비스로 분리하기 용이하다

**대안**

- FastAPI 별도 서버: Python 생태계 활용과 구조적 장애 격리가 가능하나, 언어가 하나 더 늘고 서비스 간 인증 설계가 필요하다

**결과**

- 스레드 풀 격리 설정이 누락되면 `NFR-EXT-001`을 충족하지 못한다
- LLM API 인증정보가 API 서버 실행 환경에 존재하게 된다

**관련 요구사항** FR-AI-001~008, NFR-EXT-001~003, NFR-CRED-003

### **ADR-004 — 소셜 로그인 제공자를 Kakao 단독으로 한정**

**상태** Accepted

**맥락**

`FR-AUTH-001`은 소셜 로그인 기반 회원가입을 요구한다. 국내 중고거래 서비스가 대상이며 제공자를 늘릴수록 연동·검증 비용이 증가한다.

**결정**

- 1차 릴리스는 Kakao만 지원한다
- 계정 식별자는 Kakao 회원번호를 사용한다
- 이메일은 선택 수집 항목으로 취급하며 계정 식별에 사용하지 않는다
- 이메일이 동일하더라도 계정을 자동 병합하지 않는다
- 관리자 계정은 별도 인증 수단을 두지 않고 기존 계정에 ADMIN 역할을 부여하는 방식으로 처리한다

**근거**

- 국내 사용자 커버리지가 높고 한국어 문서가 제공된다
- 카카오는 이메일 제공이 선택 동의 항목이므로 이메일 기반 식별은 실패할 수 있다

**대안**

- Google 병행: 커버리지는 넓어지나 연동·테스트 비용이 두 배가 된다
- 자체 계정 가입 병행: 비밀번호 저장·재설정 책임이 추가된다

**결과**

- 카카오 서비스 장애 시 로그인이 불가능하다
- 제공자 추가는 2차 확장으로 미룬다

**관련 요구사항** FR-AUTH-001~003, NFR-AUTH-005

### **ADR-005 — JWT 기반 인증과 Refresh Token 화이트리스트**

**상태** Accepted

**맥락**

API 서버와 채팅 서버가 분리되어 인증 상태를 공유해야 한다. `NFR-AUTH-003`은 로그아웃·탈퇴 후 기존 인증 수단의 무효화를 요구하는데, 표준 JWT는 만료 전까지 폐기가 불가능하다.

**결정**

| **구분** | **Access Token** | **Refresh Token** |
| --- | --- | --- |
| 형태 | JWT | JWT 또는 무작위 문자열 |
| 유효기간 | 30분 | 14일 |
| 검증 | 서명 검증만 | Redis 화이트리스트 조회 |
| 클라이언트 보관 | 메모리 | HttpOnly·Secure 쿠키 |
- 발급된 Refresh Token은 Redis 화이트리스트에 등록하고, 등록되지 않은 토큰은 거부한다
- 재발급 시 기존 Refresh Token을 폐기하고 새로 발급한다(Rotation)
- 이미 사용된 Refresh Token이 재사용되면 해당 사용자의 전체 토큰을 무효화한다
- 로그아웃 시 화이트리스트에서 제거한다
- 서명 알고리즘은 대칭키(HS256)를 사용하며, `alg` 값을 서버에서 고정 검증한다

**근거**

- 화이트리스트는 블랙리스트와 달리 저장소 조회 실패 시 거부 측으로 동작하여 안전하다
- Rotation과 재사용 탐지로 토큰 탈취에 대응할 수 있다
- 채팅 서버는 서명 검증만으로 인증이 가능하여 중앙 세션 의존이 없다

**대안**

- 서버 세션: 즉시 폐기는 단순하나 채팅 서버가 세션 저장소를 공유해야 한다
- JWT 블랙리스트: 명시적으로 등록된 토큰만 차단되어 누락 시 통과한다

**결과**

- Redis 장애 시 토큰 재발급이 불가능하다
- Access Token은 30분간 폐기할 수 없으므로 이용정지 반영에 지연이 발생한다

**관련 요구사항** FR-AUTH-003, 004, NFR-AUTH-002~004, NFR-AUTH-012

### **ADR-006 — 역할과 소유권의 2단 접근 제어**

**상태** Accepted

**맥락**

`FR-AUTH-006`은 역할 기반 구분을, `FR-AUTH-007`은 소유권 기반 제한을 요구한다. 중고거래에서 판매자와 구매자는 고정된 신분이 아니라 거래별 역할이다.

**결정**

- 역할은 `USER`와 `ADMIN` 두 가지로 한정한다
- 판매자는 별도 역할로 정의하지 않는다
- 모든 보호 리소스는 역할 검증과 소유권 검증을 함께 수행한다

| **검증 층** | **대상** | **예시** |
| --- | --- | --- |
| 역할 | 관리자 전용 기능 | 신고 처리, 회원 상태 변경 |
| 소유권 | 본인 리소스 | 게시글 수정·삭제, 프로필 수정 |
| 당사자 | 거래 관계 | 거래 상태 변경, 채팅 조회, 후기 작성 |
- 판매 관리 화면은 별도 역할이 아니라 본인 리소스만 조회하는 화면으로 구현한다
- 권한 검증은 서버에서만 수행하며 클라이언트 화면 제어에 의존하지 않는다

**근거**

- C2C 거래에서 판매자 역할을 신분으로 고정하면 동일 사용자의 구매·판매 전환이 부자연스러워진다
- 소유권 검증은 엔드포인트마다 개별 적용되어야 하므로 공통 처리 방식을 명시할 필요가 있다

**대안**

- USER/SELLER/ADMIN 3역할: 화면 구분은 명확하나 판매자 전환 절차가 필요하고 후기·거래 모델과 충돌한다

**결과**

- 소유권 검증 누락은 미들웨어 수준에서 일괄 방지되지 않으므로 엔드포인트별 점검이 필요하다
- 관리자 화면이 별도로 존재하므로 서버 측 역할 검증 누락 시 우회 가능성이 있다

**관련 요구사항** FR-AUTH-006, 007, FR-TRADE-008, NFR-AUTH-006~010

### **ADR-007 — 거래를 독립 엔티티로 모델링**

**상태** Accepted

**맥락**

거래 상태를 게시글의 필드로 둘 것인지 독립 엔티티로 둘 것인지에 따라 후기, 거래 이력, 알림의 구조가 달라진다.

**결정**

- 거래를 게시글과 분리된 엔티티로 정의한다
- 거래는 게시글, 판매자, 구매자, 상태를 가진다
- 게시글의 노출 상태(판매중·예약중·거래완료)는 거래 상태 변경에 따라 시스템이 전환한다
- 상태 전이 이력은 덮어쓰지 않고 별도로 보존한다

| **거래 상태** | **게시글 노출 상태** |
| --- | --- |
| 요청 | 판매중 |
| 승인 | 예약중 |
| 완료 | 거래완료 |
| 취소 | 판매중 |

**근거**

- 후기는 거래 단위로 작성되며 상대방을 특정해야 하므로 게시글 필드로는 표현할 수 없다
- 거래 취소 주체와 시점을 기록하려면 독립 레코드가 필요하다
- 동일 게시글에 대한 복수 거래 요청을 관리할 수 있다

**대안**

- 게시글 상태 필드: 구현은 단순하나 후기·거래 이력·취소 추적이 불가능하다

**결과**

- 게시글과 거래의 상태 동기화 로직이 필요하다
- 동시 요청 시 하나의 게시글에 복수 거래가 승인되지 않도록 직렬화해야 한다

**관련 요구사항** FR-TRADE-001~009, FR-LIST-010, NFR-DATA-009

### **ADR-008 — 거래 완료 확정 주체를 구매자로 한정**

**상태** Accepted

**맥락**

거래 완료를 누가 확정할지에 따라 미확정 거래의 발생 양상이 달라진다.

**결정**

- 거래 완료는 구매자만 확정할 수 있다
- 판매자는 완료를 확정할 수 없다
- 완료 확정 이후 양측 모두 후기를 작성할 수 있다
- 완료 이전에는 양측 모두 거래를 취소할 수 있다

**근거**

- 물품 수령 여부가 거래 성립의 실질적 기준이며 이를 아는 주체는 구매자다
- 판매자 단독 확정은 물품 미전달 상태에서의 임의 완료를 허용한다
- 양측 확인 방식은 한쪽이 응답하지 않을 경우 거래가 종결되지 않는다

**대안**

- 판매자 단독: 판매 이력 관리에는 편하나 구매자 보호가 약하다
- 양측 확인: 정확하나 미종결 거래가 누적된다

**결과**

- 구매자가 확정하지 않으면 거래가 승인 상태로 유지된다
- 일정 기간 경과 후 자동 완료 처리는 2차 확장에서 검토한다

**관련 요구사항** FR-TRADE-006, FR-REVIEW-001

### **ADR-009 — PostgreSQL을 단일 데이터 저장소로 사용**

**상태** Accepted

**맥락**

거래 상태 전이, 소유권, 중복 방지는 트랜잭션과 제약조건을 요구한다. `FR-LIST-008`의 검색은 별도 검색엔진 없이 처리하기로 했다.

**결정**

- PostgreSQL을 업무 데이터의 단일 저장소로 사용한다
- 거래 상태 전이는 행 잠금 또는 조건부 갱신으로 직렬화한다
- 관심 관계, 후기, 소셜 계정 식별자에 유일 제약을 적용한다
- 검색은 인덱스와 데이터베이스 질의로 처리하며 검색엔진을 도입하지 않는다
- 시간은 UTC로 저장하고 표시 시점에 변환한다

**근거**

- 한국어 전문검색 지원이 MySQL 대비 유리하다
- `NFR-DATA-009`의 동시성 요구를 데이터베이스 수준에서 보장할 수 있다

**대안**

- MySQL: 국내 사례가 많으나 한국어 검색 처리가 불리하다
- 검색엔진 병행: 확장성은 높으나 색인 일관성과 운영 대상이 증가한다

**결과**

- 검색 부하가 증가하면 데이터베이스에 직접 영향을 준다
- 인덱스 설계가 `NFR-PERF-001`, `002` 달성의 주요 변수가 된다

**관련 요구사항** FR-LIST-006~009, FR-TRADE-003, NFR-DATA-009, NFR-PERF-001~002

### **ADR-010 — Redis를 공유 상태 저장소로 도입**

**상태** Accepted

**맥락**

API 서버와 채팅 서버가 각각 복수 인스턴스로 운영되므로 인스턴스 로컬 메모리에 상태를 둘 수 없다.

**결정**

Redis를 다음 용도로 사용한다.

| **용도** | **근거 요구사항** |
| --- | --- |
| 채팅 메시지 Pub/Sub | NFR-AVAIL-005 |
| Refresh Token 화이트리스트 | NFR-AUTH-003 |
| 챗봇 호출 빈도 제한 | FR-AI-006, NFR-EXT-003 |
| 거래 상태 변경 분산 락 | NFR-DATA-009 |
- Redis를 데이터의 진실의 원천으로 사용하지 않는다
- 관심 등록 수 등 파생 카운터는 원본 데이터에서 재계산 가능해야 한다

**근거**

- 다중 인스턴스 환경에서 채팅 메시지 전달은 Pub/Sub 없이 불가능하다
- 토큰 무효화와 속도 제한은 인스턴스 간 공유가 전제되어야 동작한다

**대안**

- 인스턴스 로컬 메모리: 단일 인스턴스에서만 동작한다
- 데이터베이스 기반 처리: 가능하나 빈번한 조회로 부하가 증가한다

**결과**

- Redis 장애가 로그인 갱신과 채팅 전달에 영향을 준다
- Redis 접근 경로와 인증 설정이 보호 대상에 추가된다

**관련 요구사항** NFR-AUTH-003, NFR-AVAIL-001, 005, NFR-EXT-003

### **ADR-011 — 이미지 저장에 S3와 Presigned URL 사용**

**상태** Accepted

**맥락**

`FR-IMG-005`는 이미지를 애플리케이션 데이터와 분리된 저장소에 보관할 것을 요구한다. 업로드를 API 서버가 중계하면 대역폭과 메모리 부담이 발생한다.

**결정**

- 이미지는 비공개 S3 버킷에 저장한다
- 업로드는 Presigned URL 방식으로 클라이언트가 직접 수행한다
- 업로드 키는 서버가 생성하며 클라이언트가 경로를 지정할 수 없다
- Presigned URL은 짧은 유효기간과 단일 객체 범위로 발급한다
- 파일 형식과 크기는 업로드 완료 후 서버에서 재검증한다
- 검증 전 객체는 공개 경로로 제공하지 않는다

**근거**

- 대용량 전송이 API 서버를 경유하지 않는다
- 클라이언트가 전달한 형식 정보를 신뢰하지 않고 서버가 재검증한다

**대안**

- 서버 경유 업로드: 검증 시점이 단순하나 서버 자원 사용이 증가한다

**결과**

- 업로드 완료 여부를 별도로 확인하는 절차가 필요하다
- 게시글에 연결되지 않은 고아 객체 정리가 필요하다
- 버킷 정책, 공개 접근 차단, 암호화 설정이 보호 대상에 포함된다

**관련 요구사항** FR-IMG-001~005, NFR-DATA-008, 012

### **ADR-012 — 탈퇴 시 논리 삭제와 작성자 익명화**

**상태** Accepted

**맥락**

`FR-AUTH-010`은 탈퇴 사용자 콘텐츠의 작성자 정보 익명화를 요구한다. 물리 삭제 시 거래 이력과 후기가 사라져 상대방의 신뢰 정보가 왜곡된다.

**결정**

- 탈퇴는 논리 삭제로 처리하고 이후 로그인을 차단한다
- 작성한 게시글, 후기, 채팅 메시지는 유지하고 작성자 표시만 익명 처리한다
- 익명 처리된 후기는 상대방의 평점 집계에 계속 반영된다
- 소셜 계정 식별자는 단방향 해시로 변환하여 보관한다
- 진행 중인 거래는 취소 처리하고 상대방에게 알린다

**근거**

- 거래 이력과 후기를 삭제하면 남은 사용자의 신뢰 정보가 왜곡된다
- 식별자를 완전히 제거하면 이용정지 상태에서 탈퇴 후 재가입으로 제재를 우회할 수 있다
- 해시를 보관하면 동일인 판별과 식별 불가능성을 동시에 만족한다

**대안**

- 즉시 물리 삭제: 개인정보 관점은 명확하나 거래 이력과 신뢰 정보가 손상된다
- 식별자 완전 삭제: 재가입 우회를 탐지할 수 없다

**결과**

- 익명 처리 대상 필드를 누락하면 실질적 익명화가 이루어지지 않는다
- 보존기간과 최종 파기 정책은 별도로 정의해야 한다

**관련 요구사항** FR-AUTH-009~011, NFR-DATA-010

### **ADR-013 — 커서 기반 페이지네이션**

**상태** Accepted

**맥락**

게시글, 메시지, 알림 목록은 지속적으로 추가되는 데이터이며 `NFR-PERF-002`는 데이터 증가에 따른 응답시간의 선형 증가를 방지할 것을 요구한다.

**결정**

- 목록 조회는 커서 기반 페이지네이션을 사용한다
- 기본 페이지 크기는 20건, 최대 100건으로 제한한다
- 커서는 서버만 해석 가능한 형태로 발급한다
- 정렬 조건이 변경되면 기존 커서를 재사용할 수 없다

**근거**

- 오프셋 방식은 뒤쪽 페이지에서 성능이 급격히 저하된다
- 데이터가 추가되는 동안 오프셋 방식은 중복·누락이 발생한다

**대안**

- 오프셋 기반: 전체 페이지 수 표시가 가능하나 성능과 일관성에 문제가 있다

**결과**

- 전체 페이지 수와 특정 페이지 직접 이동을 제공할 수 없다
- 정렬 기준마다 커서 구성이 달라진다

**관련 요구사항** FR-LIST-006, FR-CHAT-006, FR-NOTI-002, NFR-PERF-002

### **ADR-014 — 인앱 알림 전용, 폴링 기반 조회**

**상태** Accepted

**맥락**

`FR-NOTI-001`은 알림 발송을 요구하나 외부 채널은 범위에서 제외되었다. 알림만을 위한 별도 실시간 전달 채널은 구현 부담이 크다.

**결정**

- 알림은 인앱 전용으로 제공한다
- 알림은 데이터베이스에 저장하고 클라이언트가 주기적으로 조회한다
- 별도의 실시간 전달 채널을 구성하지 않는다
- 알림 발송 실패가 원인이 된 업무 처리를 되돌리지 않는다

**근거**

- 알림 전용 실시간 채널은 1차 릴리스 범위 대비 구현 비용이 크다
- 폴링으로도 `FR-NOTI-001`~`004`를 충족할 수 있다

**대안**

- SSE 또는 WebSocket 전용 채널: 즉시성은 높으나 연결 관리 부담이 추가된다
- 채팅 WebSocket 공유: 연결은 절약되나 채팅 장애가 알림에 전파된다

**결과**

- 알림 확인에 폴링 주기만큼 지연이 발생한다
- 폴링 주기가 짧으면 불필요한 요청이 증가한다

**관련 요구사항** FR-NOTI-001~004, NFR-EXT-001

### **ADR-015 — 프론트엔드 프레임워크 선택**

**상태** Proposed — 프론트엔드 담당자 확정 후 결정

**맥락**

`4.1`은 모바일 웹 우선 반응형 웹을 요구한다. SSR은 범위에 포함되지 않으며 클라이언트 렌더링으로 구현한다. 두 후보 모두 React 기반이며 SPA로 동작한다.

**확정 사항**

- React 기반 SPA로 구현한다
- 서버 사이드 렌더링을 사용하지 않는다
- 빌드 결과물은 정적 파일로 배포한다
- 서버 상태 관리는 TanStack Query를 사용한다
- 클라이언트 상태 관리는 Zustand를 사용한다

**미확정 — 두 후보 중 택일**

| **항목** | **후보 A: React + Vite** | **후보 B: Next.js (CSR)** |
| --- | --- | --- |
| 라우팅 | react-router 직접 구성 | 파일 기반 라우팅 제공 |
| 빌드 설정 | Vite 설정 직접 관리 | 기본 제공 |
| 이미지 최적화 | 직접 구현 | next/image 제공 |
| 개발 서버 속도 | 빠름 | 상대적으로 느림 |
| 추가 학습 요소 | 없음 | App Router, 서버·클라이언트 컴포넌트 구분 |
| 배포 산출물 | 정적 파일 | static export 시 정적 파일 |

**선택 기준**

- 담당자가 Next.js 경험이 있으면 후보 B
- React 경험만 있거나 프레임워크 학습이 필요하면 후보 A
- 3주 일정에서 새로운 개념 학습이 부담되면 후보 A

**결정 기한** 개발 착수 전

**관련 요구사항** 4.1 서비스 제공 형태
