# FDD — 기능 상세 설계

| 항목 | 값 |
|---|---|
| 문서 상태 | Draft |
| 기준 버전 | 0.2 |
| 선행 문서 | BDR 0.2, NFR 0.2 |
| 목적 | 사용자·관리자·시스템의 동작, 규칙, 상태 및 예외 정의 |

## 1. 설계 원칙

- FDD는 시스템이 제공해야 할 동작을 정의하며 클라우드 제품이나 프레임워크 선택은 ADR에 맡긴다.
- 모든 보호 기능은 인증 역할뿐 아니라 대상 리소스와 사용자의 관계를 함께 확인한다.
- 클라이언트가 전달한 역할, 소유자, 가격 합계 또는 상태를 신뢰하지 않는다.
- 상태 변경 요청은 중복 전송될 수 있음을 전제로 멱등하게 처리한다.
- 삭제는 사용자 노출 중단과 실제 데이터 파기를 구분한다.
- 외부 연동 실패는 명확한 오류로 반환하고 핵심 업무 데이터의 일관성을 훼손하지 않는다.
- 사용자·관리자의 삭제 동작은 논리 삭제로 처리하고 실제 파기는 보존정책에 따른 자동 작업만 수행한다.

## 2. 액터와 권한

| 액터 | 설명 | 주요 권한 |
|---|---|---|
| Guest | 로그인하지 않은 방문자 | 공개 게시글·공지 조회, 로그인 시작 |
| User | 정상 상태의 로그인 사용자 | 프로필, 게시글, 관심, 거래, 채팅, 신고, 챗봇 |
| Suspended User | 이용 제한 사용자 | 본인 정보와 제재 상태 조회, 로그아웃. 쓰기 기능 제한 |
| Admin | 운영 관리자 | 신고 처리, 콘텐츠 조치, 사용자 상태 관리, 운영 현황 조회 |
| System | 비동기 작업과 내부 서비스 | 알림, 색인, 감사, 이미지 처리 등 허용된 내부 동작 |
| External IdP | 외부 신원 제공자 | 사용자 인증 결과와 허용된 프로필 속성 제공 |
| External LLM | 외부 AI 제공자 | 정제된 요청에 대한 답변 제공 |

관리자는 업무상 필요한 범위만 조회한다. 관리자 역할이 사용자 메시지 원문에 상시 접근할 수 있다는 의미는 아니며, 신고 조사 등 승인된 사유와 별도 감사 기록이 있어야 한다.

## 3. 공통 규칙

### 3.1 식별자와 시간

- 외부에 노출되는 리소스 식별자는 순차 증가값을 직접 사용하지 않는다.
- 모든 상태 변경 리소스는 생성 시각, 최종 변경 시각 및 버전 정보를 가진다.
- 저장 시간은 UTC를 사용하며 화면에서 사용자 지역 시간대로 변환한다.
- 사용자 화면은 24시간 이내 시각을 상대시간으로, 이후 시각을 `YYYY-MM-DD` 절대시간으로 표시한다.

### 3.2 페이지네이션

- 게시글, 메시지, 알림 및 감사 이벤트 목록은 커서 기반 페이지네이션을 기본으로 한다.
- 기본 페이지 크기는 20개, 최대 100개이다.
- 커서는 서버만 해석할 수 있고 정렬 조건이 바뀌면 재사용할 수 없다.

### 3.3 멱등성과 동시성

- 게시글 생성, 거래 요청·수락·완료, 메시지 전송에는 멱등성 키를 지원한다.
- 동일 키와 동일 요청은 최초 결과를 반환한다.
- 동일 키로 다른 내용이 전송되면 충돌 오류를 반환한다.
- 상태 변경은 현재 버전 또는 기대 상태를 확인해 분실 갱신을 방지한다.

### 3.4 오류 응답

| 코드 | 의미 |
|---|---|
| INVALID_INPUT | 형식, 길이 또는 허용값 위반 |
| UNAUTHENTICATED | 유효한 인증 없음 |
| FORBIDDEN | 역할 또는 리소스 관계상 허용되지 않음 |
| NOT_FOUND | 리소스 없음 또는 보안상 존재를 공개하지 않음 |
| CONFLICT | 현재 상태나 버전과 요청이 충돌 |
| RATE_LIMITED | 허용 호출량 초과 |
| EXTERNAL_SERVICE_UNAVAILABLE | 외부 연동 일시 실패 |
| INTERNAL_ERROR | 공개 가능한 세부정보가 없는 내부 오류 |

오류 응답은 내부 스택, 쿼리, Secret, 계정 존재 여부 등 공격에 유용한 정보를 포함하지 않는다.

## 4. 회원, 인증 및 프로필

| ID | 기능 | 상세 동작 및 인수 조건 | 관련 요구 |
|---|---|---|---|
| FR-AUTH-001 | 이메일 회원가입 | Guest는 이메일, 비밀번호, 비밀번호 확인, 닉네임과 필수 약관 동의를 제출한다. 이메일·닉네임 정책과 비밀번호 정책을 통과하면 인증 대기 계정을 생성한다. | NFR-SEC-002, 008 |
| FR-AUTH-002 | 이메일 인증 | 시스템은 10분간 유효한 일회용 인증 코드를 발송한다. 검증이 완료되면 계정을 활성화하고 재사용·초과 시도를 차단한다. | NFR-SEC-010~011 |
| FR-AUTH-003 | 이메일·비밀번호 로그인 | 유효한 자격증명과 정상 계정이면 Access Token과 갱신 경계를 발급한다. 실패 응답으로 계정 존재 여부를 공개하지 않는다. | NFR-SEC-003, 006, 011~012 |
| FR-AUTH-004 | 외부 로그인 시작 | Guest는 지원되는 제공자를 선택한다. 시스템은 위조 방지 상태값과 안전한 반환 주소를 사용해 인증을 시작한다. | NFR-SEC-001 |
| FR-AUTH-005 | 외부 로그인 완료 | 유효한 인증 응답이면 외부 식별자와 내부 계정을 연결하고 세션을 발급한다. 연결 계정이 없으면 필수 약관과 최소 프로필을 받은 후 가입을 완료한다. | NFR-SEC-003~004 |
| FR-AUTH-006 | 로그아웃 | 사용자는 현재 세션을 종료할 수 있다. 전체 기기 로그아웃을 선택하면 발급된 Refresh Token과 후속 세션을 모두 폐기한다. | NFR-SEC-004 |
| FR-AUTH-007 | 비밀번호 변경 | 사용자는 현재 비밀번호로 재인증한 뒤 새 비밀번호로 변경한다. 완료되면 현재 세션을 제외한 기존 세션을 모두 폐기하거나 전체 로그아웃을 선택한다. | NFR-SEC-008~009 |
| FR-AUTH-008 | 비밀번호 재설정 | 사용자는 이메일로 일회용 재설정 코드를 요청한다. 유효한 코드와 새 비밀번호를 제출하면 기존 모든 세션을 폐기한다. 요청 응답은 계정 존재 여부를 공개하지 않는다. | NFR-SEC-009~011 |
| FR-AUTH-009 | 외부 계정 연결 | 사용자는 재인증 후 추가 외부 계정을 연결할 수 있다. 하나의 외부 계정은 하나의 내부 계정에만 연결되고 이메일 일치만으로 자동 병합하지 않는다. | NFR-SEC-001 |
| FR-USER-001 | 프로필 조회 | User는 본인 프로필을 조회하고 다른 사용자의 공개 프로필만 조회할 수 있다. | NFR-AUTHZ-006 |
| FR-USER-002 | 프로필 수정 | User는 닉네임과 공개 프로필 이미지를 수정할 수 있다. 중복·금칙어 정책을 적용한다. | NFR-APPSEC-001 |
| FR-USER-003 | 회원 탈퇴 | 재인증 후 탈퇴를 요청한다. 진행 중 거래가 있으면 정책에 따라 차단하거나 명시적 확인을 요구한다. 계정은 즉시 로그인 불가·논리 삭제 상태가 되고 보존기간 후 자동 파기 또는 비가역 익명화된다. | NFR-DATA-007~010 |
| FR-USER-004 | 제재 상태 조회 | 제한된 사용자는 제한 범위, 시작 시각, 종료 시각 및 공개 가능한 사유를 확인할 수 있다. | BR-005 |

제품 데이터베이스에는 비밀번호 원문이나 해시를 저장하지 않는다. 자격증명 검증과 보호는 ADR에서 선택한 인증 시스템의 사용자 저장소가 담당한다.
Access Token 유효기간은 30분, Refresh Token 유효기간은 최대 14일로 통일하며 세션 폐기와 회전 규칙은 NFR-SEC-003~004를 따른다.

## 5. 중고거래 게시글과 이미지

### 5.1 게시글 기능

| ID | 기능 | 상세 동작 및 인수 조건 | 관련 요구 |
|---|---|---|---|
| FR-LIST-001 | 게시글 작성 | User는 제목, 설명, 가격, 상품 상태, 카테고리와 이미지를 입력해 초안 또는 판매중 게시글을 생성한다. | BR-001 |
| FR-LIST-002 | 유효성 검증 | 제목 2~100자, 설명 1~5,000자, 가격 0 이상, 허용 카테고리와 상품 상태를 검증한다. 수치는 정책 변경 가능 값으로 관리한다. | NFR-APPSEC-001 |
| FR-LIST-003 | 게시글 수정 | 작성자만 수정한다. 거래완료 후에는 오탈자 등 허용된 필드만 변경할 수 있다. | NFR-AUTHZ-001 |
| FR-LIST-004 | 게시글 삭제 | 작성자는 진행 중 거래가 없을 때 논리 삭제할 수 있다. 관리자는 사유를 입력해 숨김 또는 논리 삭제할 수 있다. 실제 파기는 보존정책에 따른 자동 작업만 수행한다. | BR-001, BR-006, NFR-DATA-008~010 |
| FR-LIST-005 | 목록 조회 | 공개 가능한 판매중·예약중 게시글을 커서 방식으로 조회한다. 차단·숨김·삭제 콘텐츠는 제외한다. | NFR-PERF-001 |
| FR-LIST-006 | 상세 조회 | 게시글, 판매자 공개 프로필, 관심 수 및 허용된 거래 상태를 반환한다. | NFR-AUTHZ-006 |
| FR-LIST-007 | 검색·필터 | 키워드, 카테고리, 가격 범위, 상품 상태, 거래 상태를 조합할 수 있다. | NFR-PERF-003 |
| FR-LIST-008 | 정렬 | 최신순과 가격 오름·내림차순을 제공하며 정렬 기준은 명시적이고 안정적이어야 한다. | NFR-CON-005 |
| FR-LIST-009 | 판매 상태 변경 | 작성자는 허용된 상태 전이만 수행할 수 있다. 거래 상태와 충돌하면 거부한다. | NFR-CON-001 |

### 5.2 게시글 상태

| 현재 상태 | 허용 다음 상태 | 수행자 | 조건 |
|---|---|---|---|
| DRAFT | ON_SALE, DELETED | 작성자 | 필수값과 공개 이미지 검증 완료 |
| ON_SALE | RESERVED, COMPLETED, HIDDEN, DELETED | 작성자/관리자 | 완료는 유효 거래와 연결 필요. 관리자는 HIDDEN 가능 |
| RESERVED | ON_SALE, COMPLETED, HIDDEN | 작성자/관리자 | 예약 거래가 취소되면 ON_SALE 가능 |
| COMPLETED | HIDDEN | 관리자 | 일반 사용자는 역전이 불가 |
| HIDDEN | 직전 공개 상태, DELETED | 관리자 | 복구 사유 기록 |
| DELETED | 없음 | 작성자/관리자 | 논리 삭제 상태이며 사용자 화면에서 복구 불가. 보존기간 후 시스템이 자동 파기 |

## 7. 거래

### 7.1 거래 기능

| ID | 기능 | 상세 동작 및 인수 조건 | 관련 요구 |
|---|---|---|---|
| FR-TRADE-001 | 거래 요청 | 구매자는 판매중 게시글에 거래를 요청한다. 본인 게시글에는 요청할 수 없다. | BR-002 |
| FR-TRADE-002 | 요청 수락 | 판매자만 대기 중 요청을 수락한다. 한 게시글에서 하나의 거래만 활성 상태가 될 수 있다. | NFR-CON-001~002 |
| FR-TRADE-003 | 요청 거절 | 판매자는 대기 중 요청을 거절하고 구매자에게 결과를 알린다. | BR-002 |
| FR-TRADE-004 | 거래 취소 | 참여자는 정책상 취소 가능한 상태에서 취소할 수 있다. 취소 사유와 수행자를 기록한다. | NFR-DATA-005 |
| FR-TRADE-005 | 거래 완료 | 수락된 거래에서 판매자와 구매자가 각각 완료를 확인한다. 한쪽만 확인한 동안 상태는 ACCEPTED로 유지하고 확인 정보를 보존하며, 양측 확인이 완료되는 순간 원자적으로 COMPLETED로 전환한다. | NFR-CON-001~002 |
| FR-TRADE-006 | 거래 조회 | 참여자는 자신의 거래 목록과 상태 이력을 조회한다. 관리자는 승인된 조사 범위에서 조회한다. | NFR-AUTHZ-006 |

### 7.2 거래 상태

| 현재 상태 | 허용 다음 상태 | 수행자 |
|---|---|---|
| REQUESTED | ACCEPTED, REJECTED, CANCELED | 판매자: 수락/거절, 구매자: 취소 |
| ACCEPTED | COMPLETED, CANCELED | 거래 참여자, 취소 정책 및 양측 완료 확인 적용 |
| REJECTED | 없음 | - |
| CANCELED | 없음 | - |
| COMPLETED | 없음 | - |

상태 이력과 양측 완료 확인 정보는 덮어쓰지 않고 별도 이력으로 남긴다. 실제 결제·정산은 포함하지 않으며 내부 보상 포인트만 제공한다.

이벤트 소비자는 최소 한 번 전달을 전제로 중복을 안전하게 무시해야 한다.
