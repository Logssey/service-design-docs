# ADR-019 — 소셜 계정은 온보딩에서 이메일을 선택 입력받는다

**상태** Accepted

**맥락**

ADR-016은 소셜 계정의 이메일을 "제공자가 검증된 이메일을 확실히 제공하는 경우에만 저장"하기로 했다. 카카오 이메일은 선택 동의 항목이고 비즈 앱 전환이 필요해 요청하지 않으므로, 카카오 가입자는 이메일을 가질 수 없다. 데이터베이스도 `ck_user_identities_social_credential`로 소셜 인증 수단의 이메일을 금지한다.

ADR-016은 같은 문제를 `LOCAL` 계정에서 "사용자가 직접 입력하는 경로"로 풀었지만 소셜 계정에는 그 경로가 없다. 카카오 가입자가 연락 수단을 남기고 싶어도 방법이 없다.

**결정**

- 소셜 온보딩(`POST /auth/signup`)에서 이메일을 선택 항목으로 입력받는다. 입력하지 않아도 가입은 확정된다
- 이메일 수집·이용 동의는 필수 약관과 분리된 선택 동의로 받는다. 이메일을 입력하면 동의가 필요하고, 동의 시각을 `user_identities.email_consent_at`에 기록한다. 이메일을 입력하지 않으면 동의 값을 저장하지 않는다
- 제공자에게 이메일을 요청하지 않고, 제공자의 동의 항목 설정도 바꾸지 않는다 (ADR-016 계승)
- 입력된 이메일은 `LOCAL`과 같은 소유 확인을 거친다. 가입 직후 확인 코드를 1회 자동 발송하며 코드 형식·유효기간·검증 시도·재발송 제한도 같다 (`NFR-AUTH-017`)
- 소유 확인 전에도 서비스 이용을 제한하지 않는다 (ADR-016 계승)
- 소유 확인이 끝난 소셜 이메일은 소셜 인증 수단 전체에서 한 계정에만 둔다. 입력 단계에서는 중복을 검사하지 않는다. 소유 확인 단계에서 코드가 맞더라도 같은 주소가 다른 소셜 인증 수단에서 이미 확인되어 있으면 `409 CONFLICT`로 거절한다. 데이터베이스는 확인된 소셜 이메일에만 거는 부분 UNIQUE 인덱스로 이를 강제한다
- 소셜 계정의 이메일은 연락 수단이며 식별자가 아니다. 이메일 로그인·비밀번호 재설정·계정 조회에 쓰지 않는다 (ADR-004, ADR-016 계승)
- 같은 이메일의 `LOCAL` 계정이 있어도 별개 계정이며 병합하지 않는다. 소유 확인이 끝난 이메일도 병합 근거가 아니다 (ADR-016, ADR-017 계승)
- 본인 응답(`GET /users/me`)에는 등록된 이메일 주소를 싣는다. 다른 사용자에게 보이는 응답에는 싣지 않는다
- 로그와 감사 기록에는 이메일 주소를 남기지 않는다 (`NFR-LOG-003`)
- 소셜 인증 수단에는 계속 비밀번호를 두지 않는다
- 온보딩 이후의 이메일 등록·변경은 이번 범위에 포함하지 않는다

**근거**

- 제공자 정책에 의존하지 않고 사용자 의사로 이메일을 확보한다. 원하지 않는 사용자에게는 수집하지 않는다
- 선택 항목도 필수 약관과 같은 기준으로 구분해 동의를 받는다 (개인정보보호법 제22조). 동의 시각을 남겨야 나중에 동의 사실을 증빙할 수 있다. 필수 약관 동의 시각을 `users.terms_agreed_at`에 두는 것과 같은 이유다
- 제공자가 검증하지 않은 주소이므로 서버가 소유를 확인해야 한다. 기존 발송·확인 절차와 Redis 키가 `identity_id` 기준이라 구조 변경 없이 재사용된다
- 유일성을 소유 확인 시점에 판정하면 미확인 주소로 타인의 이메일을 선점할 수 없다. 코드로 소유를 증명한 뒤에만 `409`를 주므로, 그 주소에 확인된 계정이 있다는 사실은 주소의 주인에게만 드러난다 (`NFR-AUTH-018`)
- 확인된 소셜 이메일이 한 계정에만 있으면 이메일로 사람을 찾거나 연락할 때 대상이 모호하지 않다
- 사용자는 자신이 입력한 주소를 보고 오타를 확인할 수 있어야 한다. 본인 응답에만 두면 다른 사용자에게는 노출되지 않는다

**대안**

- 카카오 이메일 동의 항목 요청: 비즈 앱 전환과 콘솔 설정 변경이 필요하고, 선택 동의라 확보를 보장하지 못한다
- 소셜 계정도 이메일 필수: 원하지 않는 사용자에게 수집을 강제하고 온보딩 이탈을 늘린다
- 소유 확인 없이 저장: 오타나 타인의 주소가 연락 수단으로 남는다
- 소셜 이메일 중복 전면 허용: 같은 주소가 여러 계정에 붙어, 이메일로 사람을 찾거나 연락할 때 대상이 모호해진다
- 입력 단계 유일성: 타인의 주소를 먼저 입력해 두기만 해도 주인이 그 주소를 쓸 수 없게 된다(선점). 온보딩의 중복 `409`가 소유 증명 없이 그 이메일의 가입 여부를 드러낸다 (`NFR-AUTH-018`)
- 입력란 옆 목적 고지만으로 수집: 선택 항목 동의를 필수 약관과 구분해 받았다는 증빙이 남지 않는다
- 본인 응답에 이메일 등록 여부만 싣기: 사용자가 입력한 주소를 다시 볼 수 없어 오타를 알아차리기 어렵다

**결과**

- `004` 스크립트가 필요하다. `ck_user_identities_social_credential`을 비밀번호만 금지하도록 바꾸고, `email_consent_at` 컬럼, 확인 시각·동의 시각 CHECK, 확인된 소셜 이메일의 부분 UNIQUE 인덱스를 추가한다. 기존 소셜 행은 이메일이 모두 `NULL`이라 이관이 없다
- 소유 확인 대상이 "`LOCAL` 계정"에서 "이메일이 등록된 인증 수단"으로 넓어진다. 이메일 로그인·비밀번호 재설정·비밀번호 변경은 계속 `LOCAL` 전용이다
- 이메일 조회의 안전성이 제공자 조건에 의존한다. `provider = 'LOCAL'` 조건 없이 이메일로 조회하면 소셜 계정이 로그인·재설정 대상으로 잡힌다
- 같은 주소로 `LOCAL` 계정과 소셜 계정이 공존할 수 있다. 소유 확인 전이라면 소셜 계정끼리도 같은 주소를 가질 수 있다
- 다른 소셜 계정에서 이미 확인된 주소를 입력한 계정은 그 주소를 확인할 수 없다. 잘못 입력한 주소를 고칠 경로가 없고, 기존 소셜 회원은 이메일을 등록할 수 없다. 등록·변경은 후속 결정으로 남긴다
- 소셜 가입자의 이메일이 개인정보 선택 수집 항목에 추가되므로 개인정보 처리방침에 반영해야 한다
- 소셜 인증 수단 하나로 임의 주소에 확인 메일을 보낼 수 있다. 계정 기준 발송 제한은 있지만 수신 주소 기준 제한은 없다
- 배포는 `004` 적용, 백엔드, 프론트엔드 순서다. 프론트엔드가 먼저 나가면 구 백엔드는 입력한 이메일을 저장하지 않고, `GET /users/me` 응답에 `email`이 없어 화면이 소유 확인 대상을 판단하지 못한다
- 탈퇴 시 인증 수단 행과 함께 이메일과 동의 시각이 삭제되므로 별도 파기 절차는 필요 없다 (ADR-018)

**관련 요구사항** FR-AUTH-002, 014, 017, NFR-AUTH-017, 018, NFR-LOG-003
