# ADR-002 — 채팅 서버를 독립 워크로드로 분리

**상태** Accepted

**맥락**

`FR-CHAT-002`는 실시간 메시지 송수신을 요구한다. WebSocket 연결은 API 요청과 근본적으로 다른 자원 사용·수명주기 특성을 가진다.

| **구분** | **API 서버** | **채팅 서버** |
| --- | --- | --- |
| 연결 | 무상태, 단발 요청 | 상태 보유, 장기 연결 |
| 자원 | CPU 중심 | 연결당 메모리 점유 |
| 재시작 영향 | 일부 요청 실패 | 전체 연결 단절 |

**결정**

- 채팅 서버를 API 서버와 분리된 워크로드로 운영한다
- 구현은 Node.js + Socket.IO를 사용한다
- 메시지 저장과 이력 조회는 API 서버가 담당하고, 채팅 서버는 실시간 전달만 담당한다
- 다중 인스턴스 간 메시지 전달은 Redis Pub/Sub을 사용한다
- WebSocket 연결 수립 시 토큰 검증과 대화방 참여 권한을 확인한다

**근거**

- 배포 주기와 스케일 기준을 독립적으로 관리할 수 있다
- Socket.IO는 재연결, 룸 관리, Redis 어댑터를 기본 제공한다
- Spring WebSocket + STOMP 대비 다중 인스턴스 구성이 단순하다

**대안**

- Spring 내 WebSocket 통합: 언어 단일화는 가능하나 배포 결합과 다중 인스턴스 구성 부담이 있다
- 폴링 방식: 구현은 단순하나 사용자 경험이 저하된다

**결과**

- 팀이 Java와 TypeScript 두 언어를 다뤄야 한다
- 메시지 저장(API)과 전달(채팅 서버) 경로가 분리되어 디버깅 지점이 늘어난다
- 전달 실패 시에도 저장된 메시지는 API 조회로 복구 가능해야 한다

**관련 요구사항** FR-CHAT-001~006, NFR-AUTH-011, NFR-AVAIL-005
