# ADR-016 — 자체 이메일·비밀번호 계정을 소셜 로그인과 병행

**상태** Accepted — 인증 수단의 저장 구조는 ADR-017 참조. 소셜 계정의 이메일 저장 기준은 ADR-019로 대체됨

**맥락**

`FR-AUTH-001`과 `FR-AUTH-003`은 소셜 로그인 기반 가입·로그인을 요구한다. ADR-004는 제공자를 Kakao로 한정하면서 "카카오 서비스 장애 시 로그인이 불가능하다"를 감수 사항으로 기록했다.

단일 소셜 제공자 구성은 두 가지를 남긴다.

- 제공자 장애나 계정 상실 시 서비스 계정에 접근할 수단이 없다. 이메일을 수집하지 않으므로 복구 경로도 존재하지 않는다
- 카카오 이메일은 선택 동의 항목이며 비즈 앱 전환이 필요해, 연락 수단 확보가 제공자 정책에 의존한다

소셜 제공자를 추가하면 커버리지는 넓어지지만, 계정 수단이 외부에 의존한다는 점은 달라지지 않는다.

**결정**

- 소셜 로그인(ADR-004)과 별도로 이메일·비밀번호 계정을 지원한다
- `provider`에 `LOCAL`을 추가한다. `LOCAL` 계정의 식별자는 서버가 발급한 UUID이며 이메일은 별도 컬럼에 둔다
- `LOCAL` 계정은 이메일을 필수로 가지며, 이메일은 `LOCAL` 범위에서 유일하다
- 소셜 계정의 이메일은 계정 식별에 사용하지 않는다. 제공자가 검증된 이메일을 확실히
  제공하는 경우에만 저장하며, 제공자별 저장 여부는 규칙 명세에서 관리한다
- 비밀번호는 고유 Salt가 적용된 적응형 단방향 해시로 제품 데이터베이스에 저장한다
- 같은 이메일이라도 제공자가 다르면 별개 계정이며 병합하지 않는다 (ADR-004 계승)
- 이메일 계정은 이메일 소유 확인을 수행한다. 미인증 상태에서도 서비스 이용을 제한하지 않는다
- 이메일 인증과 비밀번호 재설정 코드는 Redis에 저장한다 (ADR-010)
- 비밀번호 변경·재설정에 성공하면 해당 사용자의 Refresh Token을 전부 폐기한다 (ADR-005)
- 소셜 로그인 엔드포인트는 제공자를 경로 변수로 받는다 — `POST /auth/oauth/{provider}`
- 소셜 제공자 연동은 제공자별 구현을 교체할 수 있는 단일 인터페이스로 둔다

**근거**

- 제공자에 의존하지 않는 계정 수단이 생겨 소셜 제공자 장애 시에도 로그인이 가능하다
- 이메일을 확보하면 계정 복구 경로가 생긴다
- 카카오 이메일은 확보를 보장할 수 없으므로 사용자가 직접 입력하는 경로가 필요하다
- 제공자를 경로 변수와 인터페이스로 분리하면, 제공자를 추가할 때 변경이 구현체와 설정에 한정된다

**대안**

- 카카오 단독 유지 (ADR-004): 단일 제공자 장애와 복구 수단 부재가 그대로 남는다
- 소셜 제공자 확대만 수행: 검증된 이메일을 얻기는 쉬우나 계정 수단이 여전히 외부에 의존한다. 제공자 추가는 ADR-004의 2차 확장 방침을 따르며 이번 범위에 포함하지 않는다
- 관리형 인증 서비스 재도입: 자격증명 보관 책임은 줄지만 클라우드 인프라 저장소의 범위다
- 이메일 계정 단독 전환: 기존 카카오 연동과 `NFR-AUTH-005`의 검증 대상을 잃는다

**결과**

- 자체 자격증명을 보관하므로 인증정보 보호·비밀번호 정책·인증코드 관련 요구사항의 적용 대상이 된다
- 비밀번호 유출과 재설정 오남용이라는 위험을 새로 떠안는다
- 계정 인증과 비밀번호 재설정을 위한 메일 발송 수단이 필요하다. 로컬 개발은 대역을 사용하며 운영 수단은 미결정이다
- 같은 이메일로 소셜 계정과 자체 계정이 공존할 수 있어 사용자 혼동이 발생할 수 있다
- 소셜 제공자를 추가할 때 `provider` 제약과 제공자 구현체, 설정만 변경하면 된다

**관련 요구사항** FR-AUTH-001, 003, 012~016, NFR-AUTH-001, 014~019
