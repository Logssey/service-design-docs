# ADR-017 — 인증 수단을 계정과 분리된 엔티티로 모델링

**상태** Accepted — 탈퇴 시 인증 수단 처리는 ADR-018 참조. 소셜 인증 수단의 이메일은 ADR-019 참조

**맥락**

ADR-016은 자체 이메일 계정을 도입하면서 `users.provider`에 `LOCAL`을 추가했다. 인증 수단이 회원 행의 컬럼이므로 한 계정은 인증 수단을 하나만 가진다.

이 구조는 두 가지를 남긴다.

- ADR-016이 내건 "제공자에 의존하지 않는 계정 수단"이 기존 소셜 가입자에게는 적용되지 않는다. 카카오 계정을 잃으면 해당 계정의 거래 이력·후기·평점에 접근할 방법이 없다
- ADR-004가 2차 확장으로 미룬 소셜 제공자 추가도 같은 제약을 받는다

이메일이 같은 계정을 병합하는 방식으로는 해결할 수 없다. OpenID Connect Core 규격은 `iss`와 `sub`의 조합만을 안정적 식별자로 인정하고 `email`을 식별자로 사용하는 것을 금지한다. 이메일 일치를 근거로 자동 병합하면, 공격자가 피해자의 이메일로 계정을 미리 만들어 두고 병합 이후에도 접근을 유지하는 계정 선점 공격에 노출된다.

백엔드와 데이터베이스는 아직 구현되지 않았으므로 지금은 구조 변경 비용이 설계 문서 수정에 한정된다.

**결정**

- 인증 수단을 `user_identities` 엔티티로 분리한다. `users`는 사람을, `user_identities`는 인증 수단을 표현한다
- 제공자 계정의 유일성은 `UNIQUE(provider, provider_user_id)`로 유지한다 (ADR-016 계승)
- 한 사용자가 같은 제공자를 중복 연결하지 못하도록 `UNIQUE(user_id, provider)`를 둔다
- `LOCAL` 인증 수단의 이메일·비밀번호 해시·소유 확인 시각은 `user_identities`에 둔다
- 1차 릴리스는 사용자당 인증 수단을 하나로 제한한다. 제한은 애플리케이션에서 강제한다
- 계정 연결은 이미 로그인한 사용자가 명시적으로 수행하는 경우에만 허용한다. 이메일 일치를 근거로 자동 병합하지 않는다 (ADR-016 계승)
- 탈퇴 시 처리는 ADR-018에서 정한다

**근거**

- 인증 수단 추가가 스키마 변경 없이 행 추가로 처리된다. 소셜 제공자 추가와 계정 연결이 같은 구조에서 해결된다
- 자동 병합을 금지하면서도 사용자가 주도하는 연결 경로를 남긴다
- 인증 수단 구조는 모든 인증 경로의 기반이라, 구현 이후에 변경하면 인증 로직 전반의 수정과 운영 중 데이터 이관이 함께 필요하다

**대안**

- `users.provider` 유지: 구조는 단순하나 계정 연결과 제공자 추가 시 인증 경로 전면 수정과 데이터 이관이 필요하다
- 이메일 기준 자동 병합: OIDC 규격이 금지하며 계정 선점 공격에 노출된다
- 1차 릴리스에 계정 연결 기능까지 구현: 재인증 요구와 연결 해제 정책이 추가로 필요해 범위가 커진다

**결과**

- 인증 조회에 `users`와 `user_identities` 간 조인이 추가된다
- 사용자당 인증 수단 1개 제한이 데이터베이스가 아닌 애플리케이션 책임이 된다
- 계정 연결 기능 자체는 구현하지 않는다. 구조만 확보하며 기능은 후속 결정으로 남는다

**관련 요구사항** FR-AUTH-001, 003, 010, 012, 013, NFR-AUTH-001, 014~019, NFR-DATA-010
