# PRD(Product Requirements Document)

### 1. 문서 목적

이 문서는 프로젝트를 추진하는 이유, 달성할 목표, 제품 범위와 성공 기준을 정의한다. 기능의 상세 동작은 FDD에서, 성능·보안·가용성 기준은 NFR에서, 기술 선택은 ADR에서 다룬다.

### 2. 서비스 및 프로젝트 개요

#### 2.1 서비스 및 프로젝트 요약

본 프로젝트는 웹 기반 중고거래 플랫폼을 구축한다. 사용자는 이메일과 비밀번호로 회원가입하거나 외부 신원 제공자를 통해 가입·로그인하고, 판매 게시글을 등록하며, 관심 상품을 관리하고 다른 사용자와 거래 및 메시지를 주고받을 수 있다. 거래 결과에 따라 현금 가치가 없는 내부 보상 포인트를 적립·조정한다. 운영자는 신고, 사용자 상태 및 게시글을 관리한다. 플랫폼 이용 안내를 위한 외부 LLM 기반 AI 챗봇도 제공한다.

중고거래는 프로젝트의 목적이 아니라 복합적인 서비스 요구를 제공하는 대상 도메인이다. 프로젝트의 주된 목적은 다음 역량을 설계·구현·검증하는 것이다.

- MAU 100만 명을 가정한 확장 가능한 서비스 인프라
- 인증·인가, 개인정보, Secret 및 감사 로그를 포함한 보안 설계
- 이미지, 검색, 채팅, 알림, 외부 API 등 서로 다른 부하 특성의 처리
- 장애 탐지, 복구, 배포 및 용량 관리가 가능한 운영 체계
- 소규모 팀이 운영할 수 있는 복잡도와 비용의 통제

#### 2.2 배경 및 문제 정의

단순 CRUD 예제는 대규모 서비스에서 발생하는 확장성, 비동기 처리, 실시간 연결, 데이터 일관성, 외부 서비스 장애 및 운영 보안 문제를 충분히 드러내지 못한다. 반대로 처음부터 다수의 마이크로서비스나 고가용성 구성을 무조건 도입하면 팀 규모에 비해 운영 복잡도가 과도해질 수 있다.

이 프로젝트는 실제 서비스와 유사한 도메인 흐름을 바탕으로 다음 질문에 검증 가능한 답을 만드는 데 초점을 둔다.

1. 트래픽이 증가해도 핵심 기능을 안정적으로 제공할 수 있는가?
2. 사용자·관리자·서비스 권한이 분리되고 중요 자산이 보호되는가?
3. 장애나 외부 연동 실패를 격리하고 정해진 시간 안에 복구할 수 있는가?
4. 로그, 메트릭, 추적 정보만으로 문제를 발견하고 원인을 분석할 수 있는가?

### 3. 릴리스 완료 기준

아래 항목을 모두 충족한 시점을 1차 릴리스 완료로 판단한다.

**기능**

- 정의된 기능 요구사항(FR) 전 항목이 기능 테스트를 통과한다
- 대표 사용자 시나리오(가입 → 게시글 등록 → 거래 문의 → 거래 완료 → 후기 작성)가 중단 없이 수행된다
- 신고 접수부터 관리자 조치 및 상태 반영까지 운영 기능만으로 처리 가능하다

**품질 · 비기능**

- `MUST` 등급 비기능 요구사항 전 항목에 대해 검증 방법과 검증 결과가 문서화된다
- `SHOULD` 등급 미충족 항목은 사유와 후속 계획을 기록한다
- 주요 조회 API가 목표 응답시간 기준을 충족한다
- 서비스 중단 없이 배포 및 이전 버전 복구가 가능하다

**운영**

- 주요 인증·관리 행위에 대한 기록이 조회 가능하다
- 장애 발생 시 확인 가능한 최소한의 운영 지표가 제공된다

#### 4.2. 범위 외

아래 항목은 1차 릴리스 범위에 포함하지 않는다.

**인증 및 계정**

- 지정된 제공자 외 소셜 로그인
- 다중 소셜 계정 연결
- 한 계정에 여러 인증 수단 연결
- 2단계 인증

**거래 및 정산**

- 결제 및 에스크로 → 거래 대금은 당사자 간 직접 정산한다
- 내부 포인트 및 적립금 제도
- 경매, 교환, 나눔 등 판매 외 거래 유형
- 배송 조회 및 물류 연동
- 사업자 판매자 입점 및 정산 → 개인 간 거래만 지원한다

**탐색 및 추천**

- 위치 기반 매물 탐색 및 지역 인증
- 개인화 추천 및 유사 상품 검색
- 검색엔진 도입을 통한 검색 고도화

**커뮤니케이션**

- 다자간 채팅 및 그룹 대화
- 서비스 알림의 이메일, SMS, 모바일 푸시 알림 → 인앱 알림만 제공한다
- 커뮤니티 이미지 첨부, 좋아요, 북마크, 대댓글, 실시간 커뮤니티 알림
- 커뮤니티 전용 관리자 화면 → 기존 신고 처리 흐름에서만 커뮤니티 콘텐츠를 조치한다

**운영**

- 분쟁 조정 및 고객 상담 → 신고 접수 및 처리 외 별도 상담 창구를 제공하지 않는다
- 챗봇을 통한 사용자 데이터 조회 및 운영 행위 수행
- 수익 모델 → 광고, 수수료, 유료 기능을 제공하지 않는다

**플랫폼 및 연동**

- 모바일 네이티브 애플리케이션 → 모바일 웹 우선 반응형 웹으로 제공한다
- 제휴 서비스 연동 및 외부 공개 API 제공 → 소셜 로그인 및 LLM API 연동은 범위에 포함한다
- 다국어 지원

**품질**

- 웹 접근성 지침 준수 검증
- 구형 브라우저 지원

#### 5.2. 대표 사용 흐름

#### UC-01. 가입 및 온보딩

1. 사용자가 서비스에 접속하여 로그인 수단을 선택한다
2. 소셜 로그인을 선택한 경우 외부 인증 제공자에서 인증을 완료한다
3. 기존 가입 이력이 없는 경우 닉네임 입력 및 약관 동의 화면으로 이동한다
4. 입력을 완료하면 가입이 완료되고 로그인 상태로 전환된다
5. 기존 가입 이력이 있는 경우 3~4단계 없이 로그인 상태로 전환된다
6. 이메일 계정을 선택한 경우 이메일, 비밀번호, 닉네임 입력과 약관 동의로 가입이 완료된다
7. 가입한 이메일로 소유 확인 안내를 발송하며, 확인 전에도 서비스를 이용할 수 있다

#### UC-02. 상품 등록

1. 판매자가 게시글 등록 화면에서 상품 정보를 입력한다
2. 상품 이미지를 첨부한다
3. 등록을 완료하면 게시글이 판매중 상태로 노출된다
4. 등록된 게시글은 판매 관리 화면에서 확인할 수 있다

#### UC-03. 매물 탐색 및 판매자 확인

1. 구매자가 카테고리 또는 키워드로 게시글을 탐색한다
2. 정렬 및 필터를 적용하여 목록을 좁힌다
3. 관심 있는 게시글을 관심 목록에 등록한다
4. 게시글 상세에서 판매자 프로필을 확인한다
5. 판매자의 거래 완료 건수, 평균 별점, 받은 후기를 근거로 거래 여부를 판단한다

#### UC-04. 거래 진행

1. 구매자가 게시글에서 채팅으로 판매자에게 문의한다
2. 양측이 채팅을 통해 거래 조건을 협의한다
3. 구매자가 거래를 요청한다
4. 판매자에게 거래 요청 알림이 발송된다
5. 판매자가 요청을 승인하면 게시글이 예약중 상태로 전환되고, 다른 사용자의 거래 요청을 받지 않는다
6. 판매자가 요청을 거절하면 게시글은 판매중 상태를 유지한다
7. 오프라인에서 실제 거래가 이루어진다
8. 구매자가 거래 완료를 확인한다
9. 거래가 완료 상태로 전환되고 게시글은 거래완료로 표시된다
10. 양측에게 후기 작성 알림이 발송된다

> 구매자가 완료를 확정하지 않는 경우의 자동 완료 처리는 2차 확장에서 검토한다.
> 

#### UC-05. 거래 취소

1. 거래 승인 이후 완료 이전에, 거래 당사자 중 일방이 거래를 취소한다
2. 상대방에게 취소 알림이 발송된다
3. 게시글이 판매중 상태로 복귀한다
4. 취소 주체와 시점이 기록된다
5. 취소된 거래에 대해서는 후기를 작성할 수 없다

#### UC-06. 후기 작성

1. 거래 완료 후 당사자가 후기 작성 화면에 진입한다
2. 별점과 텍스트를 입력하여 후기를 등록한다
3. 후기는 상대방의 판매자 프로필에 반영된다
4. 하나의 거래에 대해 각 당사자는 1회만 후기를 작성할 수 있다

#### UC-07. 신고 및 처리

1. 사용자가 게시글, 사용자, 메시지 중 하나를 신고한다
2. 신고 사유를 선택하고 상세 내용을 입력한다
3. 신고 내역이 운영자 화면에 접수된다
4. 운영자가 신고 내용을 확인하고 조치를 수행한다
5. 조치 결과가 기록되고 신고자에게 처리 결과가 통지된다
6. 조치 대상이 게시글인 경우 숨김 또는 삭제 처리된다
7. 조치 대상이 사용자인 경우 이용정지 처리되며, 정지된 사용자는 로그인 이후 서비스 이용이 제한된다

#### UC-08. 사용자 차단

1. 사용자가 특정 상대를 차단한다
2. 차단된 상대의 게시글이 목록에서 노출되지 않는다
3. 차단된 상대와의 신규 채팅이 제한된다
4. 차단은 신고와 독립적으로 동작하며 운영자 조치를 수반하지 않는다

#### UC-09. 문의 응답

1. 사용자가 챗봇 화면에 진입한다
2. 추천 질문을 선택하면 사전 정의된 답변이 제공된다
3. 직접 질문을 입력하면 외부 연동을 통해 답변이 생성된다
4. 서비스 안내 범위를 벗어난 질문에는 답변할 수 없음을 안내한다
5. 외부 연동 실패 시 오류 상태를 안내한다

#### UC-10. 운영 관리

1. 운영자가 관리자 화면에 접근한다
2. 접수된 신고 내역과 회원 목록을 조회한다
3. 회원 상태를 변경하는 경우 변경 사유를 함께 기록한다
4. 수행된 관리 행위는 기록으로 남아 사후 조회가 가능하다

#### UC-11. 회원 탈퇴

1. 사용자가 탈퇴를 요청한다
2. 진행 중인 거래가 있는 경우 해당 거래는 취소 처리되고 상대방에게 알림이 발송된다
3. 계정이 탈퇴 상태로 전환되고 이후 로그인이 제한된다
4. 사용자가 작성한 게시글, 후기, 메시지는 삭제되지 않으며 작성자 정보만 익명 처리된다
5. 익명 처리된 후기는 상대방 프로필의 평점 집계에 계속 반영된다

#### UC-12. 커뮤니티 이용

1. 사용자는 로그인하지 않아도 최신순 게시글 목록과 상세, 댓글을 조회한다
2. ACTIVE 상태 회원은 카테고리를 선택해 게시글을 작성한다
3. 작성자는 자신의 게시글만 수정하거나 삭제한다
4. 활성 회원은 상세 화면에서 평면 텍스트 댓글을 작성하고, 댓글 작성자는 자신의 댓글만 삭제한다
5. 로그인 사용자의 목록과 댓글에는 자신이 차단한 사용자의 콘텐츠가 노출되지 않는다
6. 탈퇴 회원의 기존 글과 댓글은 유지하되 작성자 정보는 익명으로 표시한다

### 7. 비기능 요구사항

우선순위는 다음과 같이 정의한다.

- `MUST`  → 초기 릴리스 승인에 필수
- `SHOULD` → 미충족 시 사유와 후속 계획을 기록해야 함
- `MAY` → 일정과 비용에 따라 선택

#### 7.1. 인증 / 인가

| NFR-AVAIL-004 | MUST | 개별 인스턴스 장애가 전체 서비스 중단으로 이어지지 않아야 한다 | 인스턴스 종료 시험 |
| NFR-AVAIL-005 | MUST | 실시간 통신 기능은 다중 인스턴스 환경에서 동일하게 동작해야 한다 | 다중 인스턴스 메시지 전달 시험 |
| NFR-AVAIL-006 | MUST | 서비스 구성 요소의 정상 동작 여부를 확인할 수 있어야 한다 | 상태 점검 엔드포인트 확인 |

#### 7.7. 기록 / 감사

| ID | 우선순위 | 요구사항 | 검증 방법 |
| --- | --- | --- | --- |
| NFR-LOG-001 | MUST | 주요 인증, 거래, 관리 행위는 발생 시점, 주체, 대상을 포함하여 기록되어야 한다 | 로그 항목 검토 |
| NFR-LOG-002 | SHOULD | 기록된 감사 로그는 임의로 변경되거나 삭제되어서는 안 된다 | 권한 및 저장 경계 검토 |
| NFR-LOG-003 | MUST | 로그에는 인증정보, 토큰, 개인정보가 평문으로 포함되어서는 안 된다 | 로그 샘플 점검 |
| NFR-LOG-004 | SHOULD | 감사 로그는 허용된 역할만 조회할 수 있어야 한다 | 역할별 조회 시험 |
| NFR-LOG-005 | MAY | 로그는 사후 분석이 가능한 기간 동안 보관되어야 한다 | 보관 설정 확인 |
